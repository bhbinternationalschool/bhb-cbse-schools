# write-path — THE WRITE PATH — how a save leaves the browser and what the server does with it (origin/main 2f0eb3d4 vs live rev 00856)

## summary
For this lens the live revision 00856 is byte-identical to origin/main in every file I read except lib/mastersPersistence.ts (the 7-line PR #578 fix) and lib/masters.ts (15 lines of staff-slice preservation in hydrateMastersFromMirror), so everything below applies to production today. The write path is now mostly version-safe for ROWS: stamped desks (admissions, attendance, staff-attendance, exams, accounts, ptm, library, payroll, vault, statutory, rte, staff) send only changed rows with the updated_at they loaded and the server does a conditional UPDATE; rev desks (transport, trust, 13 desk-slice modules) send _rev bases; masters saves sections under masters_write_slices; module_local_state and domain blobs are CAS-locked on updated_at. What is NOT version-safe is (a) SIS, which still pushes all ~713 students on every edit and treats every row someone else touched since this browser's load as a "conflict" toast, (b) fees and homework, which push the whole desk with no row versions, and (c) every settings/object slice (module_registry.enabled, staff_hr.leaveSettings, homework settings, attendance policy, rbac.mobile) which is written as sent. The bigger cause of the director's six symptoms, however, is not the write path losing data but the complete absence of any server-to-client change signal: there is no realtime channel, no polling of *_desk_sync_meta, no If-None-Match from the browser, and no refresh on tab focus — a browser learns of another device's save only when a route change happens more than 15 s after its last load, and even then only the 10 component files that listen for bhb-masters-updated repaint. Two amplifiers make this worse: every row conflict on a stamped/rev desk calls ensureAllDeskHydrated(), which re-fetches EVERY desk including the four heavy on-demand ones (sis-roster 1.9 MB, fees-vouchers 1.5 MB, admissions, attendance); and the server's probe-gated response cache has a 5 s probe TTL plus table lists that omit the fee/attendance ancillary tables, so a day-close, cheque, installment plan or attendance policy saved on one PC is served stale to the next GET until an unrelated voucher or mark changes. Two "unknown becomes fact" paths remain: the staff hydrate wipes the in-memory roster on any 200 that carries three empty lists, and the mobile API's loadServerMasters() falls back to defaultMasters() (random demo ids) and caches that for 30 s on any read error, so every app request on that instance resolves classes/subjects/roles against made-up masters for half a minute.

## findings

### 1. [root] No server→client change signal exists; the only refresh is a 15 s TTL re-read on route change, and only 10 component files repaint on it  (read-in-code; S3,S5,S1)
After browser A saves (masters, staff, sis, anything), browser B has no way to learn of it: there is no Supabase realtime channel, no poll of *_desk_sync_meta, no ETag/If-None-Match round trip from the browser (every desk GET is fetch(..., cache:'no-store') with no conditional header), and the only visibilitychange handler flushes pending SAVES on hide — it never re-reads on show. B re-fetches a desk only when AppShell's pathname effect calls startDeskHydrationBackground → ensureDeskHydratedPriority and that desk's isDeskHydrated() 15 s window has lapsed. When the re-read lands, writeMastersLocalRaw replaces the memory copy and dispatches 'bhb-masters-updated', but only 10 component files listen; HomeworkWorkspace, for example, calls loadMasters() once per academic year inside a useEffect([ay]) and never again. So a teacher who stays on one screen, or whose screen read Masters at mount, keeps the old classes/subjects/fee heads until a full reload — exactly S3/S5 as reported.
