# read-path — THE READ PATH AND HOW SCREENS CONSUME DESKS (web loaders, screen mounts, re-render triggers, denormalised copies)

## summary
Live revision 00856 matches origin/main 2f0eb3d4 for every file read here except lib/masters.ts (15 lines) and lib/mastersPersistence.ts (7 lines, PR #578), so all findings apply to production. (1) Every desk loader except fees re-parses and re-normalises the whole desk on every call: loadMasters() JSON.parses the ~235 KB masters string and runs ensureFeeSetup (which rebuilds every staff/holiday/subject row) per call; loadSis() additionally calls loadMasters(), parses the ~1.9 MB roster, normalises 713 students + households, runs alignSisToMasters, then JSON.stringifys the whole roster again (slimSisJson) just to compare it with the cached string, and finally runs two side effects (syncSisIntoMasters, a dynamic import). There is no parse memo keyed on the string anywhere but lib/fees.ts (feesWorkingCopy). 484 loadMasters() and 430 loadSis() call sites exist; the shell's UniversalSearchBar re-parses masters+sis+fees+admissions per keystroke, and computeStudentDues() re-parses the transport desk once per student (713× for the home defaulter tile, ≤80× per fee-counter search). This is S4 and, on phones, the web half of S6. (2) The roster hydrate never announces itself: 'bhb-sis-updated' is dispatched only from saveSis(), and CoreDataGate waits for masters (+staff ≤5 s) but never for sis. Screens that read loadSis()/loadMasters() once in a mount effect and have no listener and no explicit ensureSisHydrated() — Attendance, Timetable, Homework, Students (masters half), PTM, RTE, Events, UDISE, Reports and ~30 panels — keep the pre-hydrate copy for the life of the mount: S1 (teachers empty on Timetable/Attendance), S2 (empty registers), S3, S5. (3) Because masters is no longer in localStorage, localMastersIsEmpty() is always true, so every masters hydrate (every navigation after the 15 s TTL) "takes" the server desk and fires 'bhb-masters-updated'; 20 useAccessData consumers plus ErpSidebar re-run loadMasters() on each, AppShell fetches /api/session/ay, and the director's PrincipalCockpit re-fetches the 5 s /api/v1/principal/snapshot on every such event and on window focus. (4) Reads have writes inside them: loadSis() can POST masters (ensureStudentClassLinks → saveMasters), writes masters and dispatches 'bhb-masters-updated' (syncSisIntoMasters), and loadMasters() writes back when staff statuses are non-standard. (5) Server side, 62 /api/v1 route files call ensureSisHydratedServer(), which re-fetches the whole roster (5 paged queries) on every request with no TTL; the principal snapshot runs six such hydrates per request, and the mobile home screen awaits guardianName → snapshot → features serially (S6). Denormalised copies are mostly ids resolved at read time; the persisted names are receipt/charge-voucher head names, homework teacherName, certificate classLabel and exam-paper className, and exam subjects are linked to Masters by code, not id.

## findings

### 1. [root] Every desk read re-parses and re-normalises the whole desk; loadSis() also re-serialises it and calls loadMasters() first  (read-in-code; S4,S6)
readCache() returns the desk as a JSON string (browserStorage.ts:258-268). loadMasters() JSON.parses it and runs ensureFeeSetup → ensureFoundationOnMasters, which maps every staff record through normalizeStaffRecord, every holiday through normalizeHoliday, subjects through ensureSubjectGroups and filters classSubjects, then four ensure*FeeStructure202627 passes and normalizeMastersStaffRoster — on every call, with no memo. loadSis() calls loadMasters() (plus ensureStudentClassLinks), JSON.parses the ~1.9 MB roster, maps 713 students through the 150-line normalizeStudent and every household through normalizeHousehold, runs alignSisToMasters, then builds slimSisJson(next) — a full JSON.stringify of the roster with stripEmptyList copies — purely to compare with the cached string, then runs syncSisIntoMasters and a dynamic import of feeDiscountImportHydrate. Only fees has a parsed working copy (feesWorkingCopy). With 484 loadMasters() and 430 loadSis() call sites, the same multi-megabyte parse+stringify runs dozens of times per screen. Cost estimate (INFERENCE from payload sizes, not measured): parse 1.9 MB ≈ 10–25 ms and stringify ≈ 10–20 ms on an office PC, several times that on a budget Android phone; one loadSis() ≈ 40–80 ms desktop / 200–500 ms phone, so a fee-counter mount (2× refresh) or a defaulter scan is hundreds of ms of pure main-thread parsing.

### 2. [root] Roster hydration never tells screens; CoreDataGate waits for masters+staff but not sis; read-once screens keep the empty/stale copy  (read-in-code; S1,S2,S3,S5)
'bhb-sis-updated' is dispatched only inside saveSis() (an edit), never when hydrateSisOnce → writeSisLocalRaw lands the roster from the server. CoreDataGate renders children once hasDeskLoaded('masters') and waits ≤5 s for staff, then gives up silently; it never waits for sis, which is the largest desk (1.9 MB) and is fetched in parallel through the 6-slot gate behind rbac/masters/moduleRegistry/route desks. A screen whose mount effect does `setSis(loadSis())` once and has no listener and no own ensureSisHydrated() therefore shows an empty register whenever its mount beats the roster GET — and nothing re-renders it later. The same holds for masters/staff on screens that have no 'bhb-masters-updated' listener: Timetable's teacherOptions, Attendance's class/section pickers and Homework's class/subject pickers are useMemo over a masters state read once. Only 9 addEventListener('bhb-masters-updated') and 3 'bhb-sis-updated' listeners exist in the whole app (components/shell, dashboard, Exams, Staff, RolesPermissionsPanel, WaNumberGapBanner). Side note: writeSisLocalRaw → syncSisIntoMasters does dispatch 'bhb-masters-updated' the first time the masters.students projection changes, which is why Staff and Exams (which listen) usually recover, while the screens listed in tables_markdown do not.

### 3. [major] Every masters hydrate after the 15 s TTL re-takes the server desk and fires 'bhb-masters-updated', fanning out re-parses, a session fetch and a 5 s snapshot fetch  (read-in-code; S4,S6)

AppShell calls startDeskHydrationBackground(pathname) on every pathname change, which re-runs the CORE tier (rbac, masters, moduleRegistry, sis) once the 15 s isDeskHydrated TTL has lapsed. ### 4. [major] Reads perform writes: loadSis() can POST masters, rewrites the masters copy and dispatches events; loadMasters() writes back during read  (read-in-code; S1,S4)

### 8. [minor] Denormalised Masters data in other desks: persisted names and code-links that a Masters rename/delete does not reach  (read-in-code; S3,S5)
Most cross-desk references are ids resolved at read time (sis student.classId/sectionId, timetable slot subjectId/teacherId/classId/sectionId, staff classTeacherLinks/subjectTeachingLinks, transport routeId/stopId), so a rename propagates and a delete cascades only where the remove handler filters (removeClass/removeSection filter classSubjects and staff links; other desks are left dangling and filtered at render). Names are frozen at write in: fees VoucherLine.label/studentName (receipt lines, intentionally frozen) and ChargeVoucherLine.feeHeadName (normaliser falls back to 'Fee'); homework posts/diary teacherName; certificates classLabel; examPapers className. Exams keeps its own ExamSubject catalogue linked to Masters subjects by CODE (syncExamSubjectsFromMasters at render, 'Exam subjects have their own ids; match by code'), so a subject code change in Masters silently unlinks marks grids. alignSisToMasters (run on every loadSis) silently moves a student to the FIRST section of the class when their section id disappears, and to a name-matched masters.students row otherwise — a Masters section delete/re-create therefore re-files children without a save.

## open questions
- Actual per-call timings were not measured (no dev server allowed); the ms estimates in finding 1 are inferred from payload sizes and should be confirmed with a performance.mark around loadSis()/loadMasters() in a browser against production.
- How long office tabs stay open without navigation: the 15 s TTL re-hydrate (finding 3) only fires on route change, so a tab parked on Attendance all morning never refreshes Masters or the roster at all — the opposite failure to the fan-out.
- Teacher logins receive a teachingOnly Masters (mastersNormalizedClient.ts:414-421) that is ALWAYS taken as changed:true; whether that view omits staff/sections some teacher screens rely on was not checked.
- Whether the fees IndexedDB path (hydrateFeesStore after ensureFeesHydrated in FeeTakeWorkspace:567-571) can replace the just-fetched server copy with an older IDB copy when remoteCount > localCount was not traced to the end.
- Which concrete device/time produced each director report (S1/S2) is unknown; the read-once list says where it CAN happen, not which instance did.
