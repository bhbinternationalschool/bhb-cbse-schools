# enforcement.

# Two migration files sharing one numeric prefix. The prefix is the migration
# VERSION, not a sort hint — Supabase keys schema_migrations on it, so a
# collision means one file can be recorded as already-applied and skipped on a
# fresh database, and which of the pair sorts first is arbitrary.
#
# Found 2026-08-24 when three sessions numbered migrations the same afternoon:
# 20260823220000 and 20260823230000 each had an inventory file and a village
# file. Both village files were still untracked and were moved to free slots
# (…215000 / …225000), verified by applying the whole set to an empty database
# in filename order. The remaining 1 is 20260814170000 (chat_messages +
# fleet_edge_events), long since committed and both applied — harmless where it
# sits, not worth rewriting history for.
#
# That last sentence was WRONG, and 2026-08-25 proved it. `version` is the
# PRIMARY KEY of supabase_migrations.schema_migrations, so a colliding pair
# makes a fresh `supabase db push` impossible: the first file of the pair is
# recorded, the second dies on a duplicate key, and the apply stops there —
# 156 of 222 migrations in, on the verification project. It is invisible on any
# database where the migrations have already run, and invisible to a raw
# `psql -f` rehearsal, which never touches the history table at all.
#
# fleet_edge_events was renumbered to 20260814171000 (the two files are
# independent, so the order between them carries no meaning). Budget is now 0
# and must stay there.
